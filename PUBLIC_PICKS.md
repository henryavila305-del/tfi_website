## Synthetic correction history

Optional corrections is a nonempty array of at most 100 records. Existing entries without it remain valid. Every record requires exactly field (odds or result), from, to, correctedAt, reason, publicApproved (true), and approvalReference (public-safe identifier). Reason/reference use the same nonempty safe-text limits as public entries.

Records use canonical UTC timestamps in nondecreasing order at or after publication. Each from must match the previous recorded value for that field, and to must change it. Odds corrections require valid integer American odds; grade corrections require pending/win/loss/push/void and cannot precede the event. Withdrawals cannot be introduced, reversed or regraded through result corrections; their separate approval record governs them. Odds recording corrections may be retained on a withdrawn entry.

The base odds and result remain unchanged. Cards label American odds as original, show the effective result plus its original value when corrected, and render an ordered correction history with old/new values, UTC times and escaped reasons. Approval references are not rendered. The public-board win percentage uses the last approved result correction; pending, push, void and withdrawn entries remain excluded. No corrected odds feed profit, units or ROI calculations. A correction fixes a recording error; later market movement must not replace the original posting price.

Full-page and narrow synthetic previews include visible corrections. Node checks cover invalid/no-op/broken chains, missing approval, invalid timestamps, unknown/private fields, multiple revisions, escaped reasons, hidden references, original-value preservation and corrected statistics. See CORRECTION_QA.md for scope and remaining checks.

This is a validated source format and static renderer, not an immutable audit service. Editing/deleting base values or prior corrections between file versions is not detected by single-snapshot validation. Actual owner approval, first-publication/source evidence, ESPN evidence and durable append-only retention remain implementation gates before real picks. Real content remains []; direct builds reject nonempty entries and Git deployment stays disabled.

## Prior-snapshot retention safeguard (synthetic only)

validatePublicPickTransition(previous, candidate) validates both snapshots, matches existing records by ID, rejects removed/renamed records, and preserves every original field including odds/result and existing withdrawal evidence. Existing correction arrays must remain an identical ordered prefix; only validated new corrections may be appended. Object key order and board ordering do not affect comparisons. New synthetic IDs are allowed by this comparison helper; this does not authorize real publication.

Read-only command: node scripts/check-public-pick-history.mjs <trusted-prior.json> <candidate.json>. Both paths are mandatory. Missing, unreadable, malformed or invalid snapshots fail rather than treating the baseline as empty. The command writes no files and does not publish or build. It is not a replacement for the empty-content/direct-build checks.

Tests use synthetic snapshots, including a self-consistent original-price/history rewrite that single-snapshot validation cannot detect, and verify CLI failures and unchanged real content. Existing withdrawn records are protected, but converting a previously recorded nonwithdrawn record into withdrawn changes its base result and is deliberately rejected by this comparator. A future append-only withdrawal-event model is needed for that lifecycle; do not remove history or rewrite the base result to bypass this guard.

This safeguard depends on a trusted, complete baseline supplied by the caller. It cannot detect a replaced/truncated baseline, prove owner approval or prevent removal of the checker. The current CI exercises it with synthetic records; no trusted historical baseline is connected for real picks, which remain empty. Durable baseline selection/storage and integration into any future publication path remain release gates. The original single-snapshot limitations described above still apply when the comparator is not used.
